# Running the balance simulation

Run `pnpm sim` for the gameplay gate. Run `pnpm sim:report` to regenerate [the Markdown report](sim/report.md), then inspect its diff and rerun the gate. The report command also works while a balance expectation needs review. A softlock or a broken reference player stops the run at the affected quest and tick.

## The reference playthrough

[The harness](../sim/playthrough.ts) opens the worker's `createSession` with `{ fresh: true }`. Omitting that option grants legacy automation. Each iteration advances the same works by one tick with no timer. Take, deploy, Run, buttons, shop purchases, and Hand over use the session methods. [The worker](../apps/web/app/lib/factory.worker.ts) schedules one tick per [site interval](../packages/sim/src/v8/sites/kettlewick.ts). Multiply ticks by `kettlewick.tickMs / 60_000` for minutes. The reference player acts immediately. The tick timeline is the works. [Human time](#human-time) adds reading and editing.

[The policy](../sim/policy.ts) takes the first eligible request. Bram's buttons fill and haul, and `smeltOnce` starts the batch. Ines mines vein D and unloads that ore at the depot. Odile uses a one-cart Loop to alloy steel. Elsie's two carts haul steel to the press and a grate to the depot. Harrow switches the press between a plate and a blank. Tomas cuts blanks into gears. Pell joins plates and pins into hinges. Wen sends a plate to the lathe and the cut plate back to the press. Odile's last contract packs a winch crate and then a lamp crate. The press-line program is typechecked and is not a proposed edit. The reference run does not buy. The shop check prices each convenience against the unspent purse at the hand-over that can first afford it.

## Human time

[ADR 0037](adr/0037-human-play-time.md) estimates real play as bot minutes plus overhead. The whole model is [sim/human.ts](../sim/human.ts): word rate for dialogue and quest text, a per-line rate plus a first-time cost for each new API call and concept, expected failed runs, and shop and machine inspection. Profiles are fast, average, and new to TypeScript. Average is the default. The report's Human time section is a per-quest table for that profile, with bot minutes, each overhead, human minutes, and a cumulative column, then a total line for every profile.

A quest over about 25 minutes for the average player, a stretch of about 15 minutes of machine time with no code change, or an edit that adds no new function, branch, loop, or API call, is a warning in that section. It does not fail `pnpm sim`. Writing follows the diff of the deployed project. Each quest keeps the previous files and adds the step it teaches. A swapped literal or job name, and a token diff at or below the count in `sim/human.ts`, is not new code. When a quest, a quantity, or a reference program changes, read the section before treating the bot clock as the length of the job. Change the constants only when the model itself should change.

## Adding content

1. Add the quest, machine, brick, or convenience in the game core. The harness reads the real quest list, machine list, brick and trigger gates, and shop listings. Keep prices, rewards, XP, recipes, machine timing and unlock rules there. If the game gains a new shop eligibility rule, expose the same available catalog to the shop, the bot, and the observer.
2. Run the existing player first. A quantity quest that it clears unchanged is a finding. For a new machine task or recipe, write an editor-ready TypeScript file in [sim/players](../sim/players) and register the project and proposed edit in the policy. Each entry file deploys as `main.ts` and shared code deploys under `lib/`. The gate typechecks these files against the game's editor declarations.
3. After Take and the initial purchase, the harness restores a separate session from that world and tries the previous stage for the configured trial window. A failed trial deploys the proposed edit. A successful previous program stays deployed. There is no practice waiver. Use guest `memory` for any state that must survive a session restore. The record names the reason and the previous and next program names. Trial ticks stay outside the playthrough. Check the trial's outstanding goals and retain a quest test proving the specific obstacle. The window supplies bounded evidence for this reference policy.
4. Review [the balance config](../sim/config.ts). It holds design bounds in minutes, the maximum purse/price ratio, the run and trial limits, tutorial exemptions and named expected failures. A milestone is a new unlock, Take, Hand over, or code edit. Idle intervals also end on a delivery or a newly green check. An XP plateau crosses quest boundaries until XP or level increases. Shop checks price each convenience against the unspent purse at its planned hand-over. A ratio under 1 is a shortfall. A ratio over the cap is late hoarding. Cheap items are not scored against the final purse.
5. Inspect the report before adding an expectation. Each key names one observed failure and gives a reason. A deliberate tutorial exception waives only the edit requirement. Missing or extra failure keys break CI, including a previously known problem that now passes. Remove resolved entries, regenerate the report and run `pnpm sim`. Runtime errors, softlocks and incomplete runs require a fix. Then read Human time. A warning there is not an expected-failure key. It is a long quest for the average player, or a long stretch of the works with no new program.
