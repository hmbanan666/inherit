# Running the balance simulation

Run `pnpm sim` for the gameplay gate. Run `pnpm sim:report` to regenerate [the Markdown report](sim/report.md), then inspect its diff and rerun the gate. The report command also works while a balance expectation needs review. A softlock or a broken reference player stops the run at the affected quest and tick.

## The reference playthrough

[The harness](../sim/playthrough.ts) opens the worker's `createSession` with `{ fresh: true }`. Omitting that option grants legacy automation. Each iteration advances the same works by one tick with no timer. Take, deploy, Run, buttons, shop purchases, and Hand over use the session methods. [The worker](../apps/web/app/lib/factory.worker.ts) schedules one tick per [site interval](../packages/sim/src/v8/sites/kettlewick.ts). Multiply ticks by `kettlewick.tickMs / 60_000` for minutes. The reference player acts immediately, so the timeline excludes time spent reading and editing.

[The policy](../sim/policy.ts) takes the first eligible request. Bram's buttons fill and haul, and `smeltOnce` starts the batch. Ines mines vein D and unloads that ore at the depot. Odile uses a one-cart Loop to alloy steel. Elsie's two carts haul steel to the press and a grate to the depot, and the same file keeps the later ingot and steel jobs. The press-line program is typechecked and is not a proposed edit. The bot buys an affordable cart for a load the cart cannot hold, a hopper for a steel order whose cart exceeds the coal cap, a hotter furnace for queued ore, or CPU when it reaches the limit. Racks and the spare press are not bought by the reference player. Each purchase uses the items `shopFor` lists and the live price.

## Adding content

1. Add the quest, machine, brick, or convenience in the game core. The harness reads the real quest list, machine list, brick and trigger gates, and shop listings. Keep prices, rewards, XP, recipes, machine timing and unlock rules there. If the game gains a new shop eligibility rule, expose the same available catalog to the shop, the bot, and the observer.
2. Run the existing player first. A quantity quest that it clears unchanged is a finding. For a new machine task or recipe, write an editor-ready TypeScript file in [sim/players](../sim/players) and register the project and proposed edit in the policy. Each entry file deploys as `main.ts` and shared code deploys under `lib/`. The gate typechecks these files against the game's editor declarations.
3. After Take and the initial purchase, the harness restores a separate session from that world and tries the previous stage for the configured trial window. A failed trial deploys the proposed edit. A successful previous program stays deployed. There is no practice waiver. Use guest `memory` for any state that must survive a session restore. The record names the reason and the previous and next program names. Trial ticks stay outside the playthrough. Check the trial's outstanding goals and retain a quest test proving the specific obstacle. The window supplies bounded evidence for this reference policy.
4. Review [the balance config](../sim/config.ts). It holds design bounds in minutes, the maximum purse/price ratio, the run and trial limits, tutorial exemptions and named expected failures. A milestone is a new unlock, Take, Hand over, or code edit. Idle intervals also end on a delivery or a newly green check. An XP plateau crosses quest boundaries until XP or level increases. Shop checks sample the purse before spending, for each listing and for the total price when several arrive together.
5. Inspect the report before adding an expectation. Each key names one observed failure and gives a reason. A deliberate tutorial exception waives only the edit requirement. Missing or extra failure keys break CI, including a previously known problem that now passes. Remove resolved entries, regenerate the report and run `pnpm sim`. Runtime errors, softlocks and incomplete runs require a fix.
